# Architecture

SmartPricing is a Java 21 / Spring Boot modular monolith backed by PostgreSQL, with a standalone Angular application. Each installation serves one business. Tenancy is planned, not implemented.

Package by feature. `health` contains the liveness API; `business` and `catalog` separate controllers, DTOs, transactional services, JPA entities, and repositories. `sales` and `history` use the same feature boundaries with SQL repositories for immutable snapshots, range constraints and explicit locking. `config` owns web configuration; `common` owns consistent safe API errors and entity auditing/version checks. There are no empty placeholder layers for the stateless health endpoint.

PostgreSQL is the source of truth. Flyway owns migrations, and Hibernate validates JPA mappings. V1 creates an empty metadata table; V2 creates the catalog/settings; V3 adds immutable order/refund financial snapshots, effective listed-price/cost periods, and inventory observations. Current catalog values are distinct from historical realized transaction amounts. Unknown cost/inventory stays explicit; source keys provide idempotent append semantics. Verified periods have PostgreSQL overlap constraints and synchronize current catalog values atomically. Local Compose runs only PostgreSQL; neither application has a production image or hosting configuration.

## Read-only analytics

Milestone 05 adds the read-only `analytics` feature with thin controllers, typed decimal-string DTOs, testable metric rules, and focused PostgreSQL aggregate repositories. Sale and refund events are aggregated independently; historical immutable line snapshots supply financial amounts/costs. Inventory latest-observation queries preserve unknown, uncertain and stale states. Read-only repeatable-read transactions make each response consistent; no durable analytics tables or migration are needed. Angular's lazy analytics route uses accessible SVG plus exact text tables, with no new chart dependency. See [metric contract](analytics.md).

## Demand forecasting

Milestone 06's `forecasting` module adds a bounded batch daily-series repository, validated typed settings, pure guarded calendar log-OLS and weekday baseline/backtest model, read-only service and thin controllers. Runtime inputs are domain history only; no generator imports or truth-table reads. Existing archived variants remain historically queryable while current archival suppresses future forecasts. No persisted model schema or external ML library is added.

## Read-only optimization

Milestone 07's `optimization` module adds a pure grid contribution optimizer, stricter evidence gates, typed settings/DTOs, a batched effective-price/cost/stock repository, and read-only controllers. It reuses M06 batch input and pure model functions. No evaluation snapshot/history persistence, model schema, mutating GET, or apply-price endpoint is introduced. Existing immutable domain history supplies lineage; repeated evaluations are not an audit-history substitute. See [optimization.md](optimization.md).

## Authentication and connection lifecycle

Milestone 08 adds `auth` (one BCrypt administrator, explicit non-web provisioning, Spring Security server sessions, CSRF, bounded login throttling) and `shopify` (validated standalone OAuth, provider interface/HTTPS adapter, AES-GCM token encryption, transactional singleton lifecycle). V4 adds one account, one business-linked connection and expiring hashed session-bound states. It leaves business history and demo checksum untouched. Angular uses session guards and CSRF-aware relative API requests, with no bearer credential storage. Anonymous demo reads are separately guarded by live database identity and all writes are denied. See [authentication](authentication.md) and [Shopify connection](shopify-connection.md).

## Planned, not implemented

Recommendation quality improvements, high-volume bulk imports, webhook intake, interface refinement and price write-back remain future work. The pricing engine consumes normalized domain inputs through application boundaries, independently of ingestion provider. Shopify-specific payloads and transport concerns stay behind the provider boundary so file imports, demo generation, and future providers can share the same pricing engine. Pricing operations require both parent product and variant to be ACTIVE; historical ingestion may reference archived variants without rewriting snapshots.

Milestone 10's `onboarding` feature derives scoped workflow, coverage, input/provenance findings and per-variant diagnostics without a migration or writes. Summary uses aggregates; pages select at most ten variants before batched series/market/coverage queries. Existing pure forecast/optimization gates supply exact statuses and reasons; no new readiness model, stored certificate, recommended price or bypass is introduced. Current-input timestamps and retrospective model time are distinct. Merchant completion reuses catalog/history validation and retains the conservative local/provider conflict policy. Demo configuration surfaces are read-only. See [onboarding contract](onboarding.md).

Seeded demo mode is implemented in `demo`: a pure deterministic generator, transactional orchestrator, private metadata/checksum repository, explicit command runner and database identity guard. A separate Compose project/database/role on port 5434 isolates it from normal development. An admin-owned marker cannot be changed by the application role. Migration and command guards fail closed before business writes; reset additionally requires explicit confirmation. Source DEMO is rejected by ingestion services in normal mode. Ordinary startup never seeds. The read-only environment API drives the Angular synthetic-data indicator; demo summary is available only in demo mode. Generator ground truth stays in private demo metadata and is not an analytics input. See [demo-data.md](demo-data.md).

Milestone 09's `shopify.sync` module adds read-only GraphQL transport, literal bounded query documents, mapping rules, durable jobs/checkpoints and a manual-job worker. `common/BoundedHttp` limits streaming body size and whole-response time. Separate shop-scoped mappings protect manual records and immutable source snapshots; V5 adds metadata and nullable unknown catalog cost without backfilling historical data. Provider requests happen outside canonical write transactions; connection generations are rechecked inside each atomic page commit. Expiring credentials rotate server-side under the existing singleton lock before jobs use them. No automated import creation, webhooks, write-back, tenant layer or dormant refresh scheduler exists. See [sync contract](shopify-sync.md).

The public application health endpoint is a liveness/connectivity signal, not a pricing-readiness claim. Actuator health includes infrastructure checks. All API errors use code/message/timestamp/fieldErrors; unexpected failures return a generic message and stack traces stay in server logs. Optimistic versions reject stale updates; per-product locks serialize activation and variant changes, and singleton locking prevents currency changes racing with first-variant creation.

Dependencies are deliberately limited: Web for REST/MVC, Validation for request validation, Data JPA for persistence and schema validation, PostgreSQL JDBC, Flyway core and its PostgreSQL module, Actuator, and Spring Security. Spring Boot Test and Security Test support assertions; Testcontainers and Boot service connections provide real PostgreSQL integration tests. Angular HttpClient/router support API calls and navigation; generated Vitest/jsdom tooling supplies frontend unit tests. Shopify uses JDK HttpClient, with no external service SDK.
